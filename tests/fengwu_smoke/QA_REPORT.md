## 4. 反向注入验证（证伪"死断言"）

任务书要求：临时注入至少一个"假门槛"，验证断言确实会 FAIL，验证后还原。

**方法**：用 `FENGWU_QA_ROOT` 环境变量把门禁指向一份 `CollectionManager.gd` 沙箱副本，
**不动真实源码**。在沙箱中删除 1 个"拾得"条目，使 `FENGWU_ITEMS` 变为 **23 槽（拾得11/购得6/手作6）**，
同时保留 `const FENGWU_TOTAL := 24`（制造不一致）。

**结果（沙箱运行）**：

```
[parse] FENGWU_ITEMS=23
assertions=41  passed=34  failed=7  concerns=2  notes=6
VERDICT: FAIL   (exit 1)
```

翻红的 7 条断言：

| 断言 | 内容 | 翻红原因 |
|---|---|---|
| Q03 | `FENGWU_ITEMS` 恰含 24 槽 | 实得 23 |
| Q04 | obtain 分布 == 拾得12/购得6/手作6 | 实得 拾得11/购得6/手作6 |
| Q05 | fid 无重复 + 顺序分组 | 长度不匹配 |
| Q06 | 24 风物名唯一 | 现仅 23 名 |
| Q07 | `FENGWU_TOTAL` 常量 == 注册表实长 | TOTAL=24 ≠ 23，唯一真源一致性告警 |
| Q11 | 本 sprint 可达上限 == 18 | 现 23−6=17 |
| Q23 | mock：23/24 不授称号 | 23 件注册表下"23/23 即满"触发翻转（证明 mock 与注册表实长同源，非硬编码死值） |

**结论**：门禁在注入缺陷后**立即翻红并退出码 1**，证明 41 条断言**全部对真实数据敏感，非永远 PASS 的死断言**。验证后沙箱副本已删除，真实源码零改动（复跑基线仍 41/41 确认）。

> 复判过程中，本门禁自身的 mock 测试（原硬编码 `"liuxu"` 作桩）在变异测试下抛出 `KeyError`，
> 已就地加固为 `dummy = fids[0]`（从存活注册表取首个 fid）。这是对**测试脚本**的修正，
> 不动游戏实现——与 engineering 在 140/140 编写期"修脚本不迁就实现"（changelog §5 注）同一纪律。

## 6. 非阻塞关注项（advisory，非 FAIL，不影响放行）

### CONCERN #1 ·【拾得节奏 · 可重 roll】
- **现象**：`pick_fengwu_pickup` 挂在 `MainGame._on_location_selected` 上，而"进入地点"本身不调用 `advance_time()`（`advance_time` 仅由 `DialogueUI/MainGame/StudySubjectPopup` 触发）。且 `FENGWU_PICKUP_DAY_FLAG` **只在 roll 成功后**才写，失败不消耗当日额度。
- **后果**：玩家可在**同一时段反复进出同一地点**重复 roll，把 0.18~0.42 的概率刷成"每天必得 1 件"。每日 1 件上限仍在，危害上限 ≈ 12 天集齐全部拾得。
- **危害评级**：低。**无 soft-lock、无崩溃、无经济外溢**（拾得不耗钱、不耗时段、不影响其它系统）。
- **建议**：若该节奏为刻意设计可忽略；若想守住"概率感"，把 `set_flag(FENGWU_PICKUP_DAY_FLAG, ...)` 移到 `randf()` 判定**之前**（消耗"尝试"而非"成功"）。

### CONCERN #2 ·【送礼池污染 · 轻】
- **现象**：`DialogueUI` 送礼面板无条件遍历 `ITEM_DB` 并列出 `inventory>0` 的物品，6 件购得风物因此全部可作礼物送出；`GIFT_PREFERENCES` 无对应条目 → 一律走兜底 **+3 好感 + 通用台词**。
- **后果**：不影响风物志进度（`fengwu_<fid>` 购买时已永久落账，送掉不回退），但 20~90 元档特产与 15 元奶茶**好感收益相同且无专属回应**，体验略糙。
- **危害评级**：低。
- **建议**：后续补 `GIFT_PREFERENCES` 条目，或将 `category=="fengwu"` 标记为不可赠送。
